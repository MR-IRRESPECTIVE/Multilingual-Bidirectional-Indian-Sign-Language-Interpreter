# Static Live Domain Analysis

## Training vs Live: Quantitative Domain Gap

### The Core Problem

The 42-feature vector produced at inference time is mathematically inverted along the X-axis compared to training vectors. This is not a subtle distributional shift — it is a complete geometric mirror.

### Mathematical Proof

Consider a right-hand landmark at raw MediaPipe position `(x=0.7, y=0.3)` on a 640×480 frame.

**Training path** (with `cv2.flip`):
```
MediaPipe receives flipped image → lm.x is already mirrored
Pixel X = floor(0.3 * 640) = 192    (0.7 becomes 0.3 after flip)
Pixel Y = floor(0.3 * 480) = 144
```

**Live path** (no flip, `processStatic42Features`):
```
MediaPipe receives raw image → lm.x is original
Pixel X = floor(0.7 * 640) = 448
Pixel Y = floor(0.3 * 480) = 144
```

**Live path** (simulated flip, `processStatic42FeaturesFlipped`):
```
Simulated: (1.0 - 0.7) = 0.3
Pixel X = floor(0.3 * 640) = 192    ← MATCHES TRAINING
Pixel Y = floor(0.3 * 480) = 144
```

After wrist-centering and normalization, the un-flipped vector will have **opposite signs** on all X-components relative to training, while the flipped vector will match exactly.

### Expected Impact on Predictions

The X-axis inversion means:
- Finger positions that should be on one side of the wrist appear on the opposite side
- The model's learned decision boundaries are based on flipped geometry
- Signs that are **horizontally asymmetric** (like Hello, A, B) will be catastrophically misclassified
- Signs that are **roughly symmetric** (like some numbers) may occasionally still be recognized

This explains the observed behavior:
- **Hello → digit_7**: The flipped Hello geometry happens to look similar to digit_7 geometry from the model's perspective
- **C → digit_1**: Flipped C landmarks overlap with digit_1 decision region
- **B → unstable**: Partially symmetric, causing oscillation between classes

### What the Flipped Function Fixes

`processStatic42FeaturesFlipped()` applies `x_simulated = 1.0 - lm.x` before pixel conversion. This mathematically restores the training domain:

$$x_{\text{flipped}} = 1.0 - x_{\text{raw}}$$

This is equivalent to what `cv2.flip(image, 1)` does before MediaPipe: it mirrors the X coordinate space.

### Why This Function Exists But Isn't Used

The `/test-static-live` A/B test page already has both functions wired up:
- Panel 1: `processStatic42Features` → `POST /api/translate/sign/static` (static_v1 model)
- Panel 2: `processStatic42FeaturesFlipped` → `POST /api/translate/test/atharv` (legacy Atharv TFLite)

However, the **main conversation page** (`/conversation`) uses the **86-feature temporal pipeline** (`processUnifiedHands`), not the static pipeline at all. The static_v1 model is only accessible via `/test-static-live`, and even there, the flipped features are sent to the **wrong model** (Atharv legacy 42-class TFLite instead of the static_v1 13-class Keras model).

### The Minimal Fix

The smallest change that fixes live accuracy is:

1. On the `/test-static-live` page: send the **flipped** features to the **static_v1** model endpoint (`/api/translate/sign/static`), not to the Atharv legacy endpoint.
2. On any future live static recognition page: always use `processStatic42FeaturesFlipped()`.
3. Do NOT change the model, do NOT retrain, do NOT modify the dataset.

### Dataset Leakage: Why 99.8% Doesn't Generalize

The train/test split is `train_test_split(X, y, test_size=0.15, random_state=42, stratify=y)`.

This is a random row split. The source datasets were generated by recording continuous webcam sessions — meaning consecutive frames are nearly identical. When these frames are randomly scattered across train and test splits, the model effectively memorizes individual recording sessions rather than learning generalizable hand geometry.

A proper evaluation requires either:
- **Source-aware split**: Train on Atharv, test on Maitree (or vice versa)
- **Session-aware split**: Group consecutive frames into sessions and split at the session level
- **Live webcam validation**: The ultimate test

Since signer IDs and session boundaries are unavailable in the legacy data, **live webcam validation is the only honest accuracy metric**.
